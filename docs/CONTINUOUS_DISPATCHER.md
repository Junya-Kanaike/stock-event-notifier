# Macに依存しない起動補助

2026-10-17からmainで有効化済みで、2026-10-22時点で稼働中です（約165分ごとに次の実行へ引継ぎ）。[Mac補助](MAC_SCHEDULER.md)も併用しています。

`continuous_dispatcher.yml` はGitHub側で約1分ごとに本番mainの処理記録を確認します。済んでいるかはstateの処理成功記録だけで判定し、ジョブ履歴は待機・実行中のジョブの確認にだけ使います。不足時だけ既存の朝同期・予定通知・TDnet巡回をmainへ起動要求します。状態更新中のジョブがあれば追加要求せず、受付が不明な同一要求も10分間は繰り返しません。

1実行は最大約165分で、終了時に次の実行を要求します。3時間ごとのcronも復旧用に残します。通知・データ更新そのものは既存の3ワークフローが担当します。補助の実行枠は状態更新用と別なので、補助の常駐によって本番の処理が待たされることはありません。状態更新ジョブは実行開始時の最新mainを取得します。

## 有効化前の条件

- 修正コードと保存データをmainに反映し、CIを確認する。
- 公開リポジトリであることを確認する。ワークフロー条件とPython側の両方で、非公開リポジトリでは常駐を開始しない。
- リポジトリ変数 `NOTIFIER_CONTINUOUS_DISPATCHER=true` を明示設定する。未設定ではジョブを実行しない。
- 追加の有料サービスや個人用アクセストークンは不要。既存のsystem Webhookと、GitHubが各ジョブに与える当該リポジトリ限定のトークンを使用する。

[GitHub公式：公開リポジトリの標準ランナー](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)は無料です。[GITHUB_TOKENの公式仕様](https://docs.github.com/en/actions/concepts/security/github_token)では、workflow_dispatchによる次のジョブ起動が認められています。

有効化・起動は本番変更として承認後に実施します。今回追加したコードだけでは変数設定も起動も行いません。

## 稼働確認

1. continuous_dispatcherがmainで実行中になっている。
2. 朝処理・予定通知・TDnetにworkflow_dispatch実行が現れる。
3. mainの`workflow_health`が実際に更新される。
4. 予定時刻内にSlackへ届く。ジョブ成功だけで到着を判定しない。
5. 次のcontinuous_dispatcherが待機し、前の実行終了後に引き継がれる。

データ鮮度超過、20分以上の待機、当日予定が15分以上未送信などをsystemへ通知します。同じ実行内では警告を1時間以内に繰り返しません。引き継ぎ後は抑止時刻がリセットされます。GitHub APIの確認に失敗した場合は、状況不明のまま起動を重ねません。

既存のMac補助と標準cronは予備として保持します。双方が同時に要求しても、状態更新用の共通実行枠と保存済み送信履歴で重複送信を抑えます。

## 停止

変数をfalseへ変更し、実行中のcontinuous_dispatcherをキャンセルします。変数変更だけの場合、現在の実行は最大約165分まで継続しますが、次の実行は開始されません。既存3ワークフローのcronとMac補助はそのまま使えます。

## 制約

GitHub全体の障害、ランナーの待機、ネットワーク障害は残ります。自分自身も含めてGitHubが全面停止した場合、この補助だけで即時検知することはできません。厳密な時刻保証や完全な外部監視を提供するものではありません。

受付直後に保存が失敗した場合の重複余地も従来どおり残ります。まず実際の営業日の巡回間隔と通知到着時刻を測ってから、改善効果を判断します。
